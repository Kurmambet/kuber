Хорошая новость — это делается одной командой, без всякого `join`/`reset`, потому что control-plane-статус ноды и её способность запускать обычные поды — это два независимых понятия. Toleration/taint — это просто **политика планировщика**, а не членство в etcd-кворуме.

## Что реально мешает node2 принимать обычные поды

При `kubeadm init`/`join --control-plane` каждая control-plane нода автоматически получает **taint** — специальную "метку-запрет":

```
node-role.kubernetes.io/control-plane:NoSchedule
```

Именно из-за неё scheduler по умолчанию не ставит туда ваши поды (только системные, у которых есть toleration к этому taint, как у Calico). Убрав этот taint — вы получите ровно то, что видели в ролике: node2 останется control-plane (etcd, apiserver и т.д. продолжат работать как работали), но при этом станет ещё и полноценным местом для обычных подов.

## Сделать node2 такой же, как в ролике

**На хосте:**

```bash
kubectl describe node node2 | grep Taints
```

Убедитесь, что видите `node-role.kubernetes.io/control-plane:NoSchedule` — это подтверждает, что именно этот taint блокирует размещение.

```bash
kubectl taint nodes node2 node-role.kubernetes.io/control-plane:NoSchedule-
```

Обратите внимание на **минус в конце** — это синтаксис "удалить" (без минуса было бы "добавить"). После этой команды node2 официально снята с ограничения.

Проверка:

```bash
kubectl describe node node2 | grep Taints
```

Должно показать `<none>` или отсутствие строки про control-plane taint.

## Заставить существующие поды пересчитаться на node2

Ваш `nginx-rs` уже создал 2 пода **до** снятия taint — они уже сидят там, где их разместил scheduler в тот момент (скорее всего оба на node3), и сами по себе никуда не переедут — Kubernetes не занимается "ребалансировкой" уже работающих подов просто так. Чтобы увидеть эффект как в ролике, нужно заставить scheduler пересчитать заново:

```bash
kubectl delete pods -l app=nginx-rs
```

ReplicaSet тут же увидит, что подов не хватает, и закажет 2 новых — на этот раз scheduler будет выбирать между node2 **и** node3 (оба без ограничений), и, скорее всего, раскидает по одному на каждую — ровно то, что было в видео.

```bash
kubectl get pods -o wide
```

Проверяем распределение.

## Как вернуть всё как было (передумали)

Ровно обратная команда — **без минуса**, чтобы снова навесить taint:

```bash
kubectl taint nodes node2 node-role.kubernetes.io/control-plane:NoSchedule=:NoSchedule
```

Или короче, современный синтаксис `kubectl taint` тоже принимает так:

```bash
kubectl taint nodes node2 node-role.kubernetes.io/control-plane:NoSchedule
```

Дальше — та же история: taint не трогает уже работающие на node2 поды (Kubernetes не выселяет их принудительно просто из-за нового taint без явного `NoExecute` эффекта), но новые поды туда больше не попадут. Если хотите, чтобы node2 сразу "очистилась" от пользовательских подов при возврате:

```bash
kubectl drain node2 --ignore-daemonsets --delete-emptydir-data
```

`drain` вежливо evict'ит (переселяет) все обычные поды с node2 на другие ноды, оставляя системные DaemonSet'ы (Calico, kube-proxy) на месте — а сразу следом наложенный taint не даст новым подам туда вернуться.

## Почему не нужно ничего пересоздавать через join

Важно закрепить: `kubeadm join`/токены (те, что "сгорели" через 24 часа) нужны только для **первого присоединения** ноды к кластеру — то есть для получения сертификатов и регистрации в etcd. node2 **уже** член кластера, её членство никуда не делось и не имеет срока годности. Taint/toleration — это runtime-настройка, которая живёт в etcd вместе со всем остальным состоянием кластера и меняется мгновенно через `kubectl`, без всякой повторной аутентификации нод. Токены нужны были бы только если бы вы захотели присоединить **новую**, четвёртую ноду.

## Почему `app-with-sidecar` удалился спокойно

Вы применили `pod-with-sidecar.yaml`, где `kind: Pod` — это создаёт **самостоятельный** под без какого-либо контроллера сверху. Никто не следит за тем, "должен ли он существовать" — вы попросили Kubernetes создать его один раз, и после `kubectl delete` он просто исчезает, как обычный процесс, который вы убили. Точь-в-точь как с `test-node1` из вашего эксперимента.

## Почему `nginx-rs` воскресает

Тут `kind: ReplicaSet` с `replicas: 2` — это **декларация желаемого состояния**: "в любой момент времени в кластере должно быть ровно 2 пода с лейблом `app: nginx-rs`". Есть отдельный контроллер (часть `kube-controller-manager`, который крутится на node1/node2), который **постоянно** сверяет реальность с этим желанием. Когда вы командой `kubectl delete pods -l app=nginx-rs` удалили оба пода — вы удалили только сами поды, а не саму декларацию "их должно быть 2". Контроллер тут же заметил расхождение (было 2, стало 0) и заказал два новых — вы это и увидели: новые имена `nginx-rs-dl9s7`/`nginx-rs-kxk9d` вместо старых `nginx-rs-7lgtp`/`nginx-rs-tj5hp`.

Это прямая параллель с `docker-compose`: если у вас в `docker-compose.yml` `replicas: 2` (Swarm-режим) и вы вручную убьёте один контейнер — Swarm пересоздаст его, потому что "желаемое состояние" описано в файле, а не в текущих запущенных контейнерах.

## Как правильно убрать `nginx-rs`

Нужно удалить не поды, а сам объект ReplicaSet — тогда контроллеру нечего будет "поддерживать":

```bash
kubectl get replicasets
```

Посмотреть, что объект называется именно `nginx-rs` (имя из `metadata.name` в манифесте).

```bash
kubectl delete replicaset nginx-rs
```

Или короче: `kubectl delete rs nginx-rs`. Это удалит саму декларацию — контроллер увидит, что ReplicaSet больше не существует, и заодно уберёт оба его пода автоматически (каскадное удаление зависимых объектов — поды принадлежат ReplicaSet'у как "дочерние" ресурсы).

Проверка:

```bash
kubectl get pods
kubectl get replicasets
```

Оба списка должны быть пустыми (по nginx-rs).

## Самый правильный способ — через манифест, а не по имени/лейблу

Раз вы применяли через `kubectl apply -f`, симметрично убирать тоже через файл — это гарантирует, что удалится именно то, что описано, без риска опечататься в имени:

```bash
kubectl delete -f <путь_к_вашему_nginx-rs.yaml>
```
