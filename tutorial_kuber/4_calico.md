Хороший вопрос для полного понимания сети — тем более что вы уже видели интерфейс `tunl0`, который как раз и есть follow-up одного из этих режимов в вашем кластере прямо сейчас.

## Три основных режима (правильнее говорить — два измерения: инкапсуляция и маршрутизация)

Calico поддерживает три способа гонять трафик между подами на разных нодах:

| Режим                               | Оверхед на пакет | Требует BGP?                   | Где применяется                                                                         |
| ----------------------------------- | ---------------- | ------------------------------ | --------------------------------------------------------------------------------------- |
| **BGP / Native (без инкапсуляции)** | 0 байт           | Да, между самими нодами Calico | Одна L2-подсеть или сеть с BGP-способными свитчами/роутерами                            |
| **IP-in-IP (IPIP)**                 | 20 байт          | Да, поверх него                | Облака и сети, где нельзя научить роутер маршрутам подов                                |
| **VXLAN**                           | ~50 байт         | Нет                            | Самая "тупая" сеть, где даже IPIP может не пройти (блокируются протоколы кроме TCP/UDP) |

Источник по цифрам overhead и сценариям. [oneuptime](https://oneuptime.com/blog/post/2026-03-13-kubernetes-networking-calico-choose-production/view)

## Что происходит в каждом режиме простыми словами

**BGP/Native** — Calico на каждой ноде запускает мини-BGP-роутер (компонент **BIRD** внутри `calico-node`), и ноды обмениваются друг с другом маршрутами: "мои поды с IP из диапазона X.X.X.X/26 находятся у меня". Дальше пакет от пода к поду на другой ноде идёт как **обычный IP-пакет** — ядро просто смотрит в таблицу маршрутизации и отправляет его напрямую через сетевую карту. Никакой "обёртки" вокруг пакета нет — отсюда нулевой оверхед и максимальная производительность. [github](https://github.com/projectcalico/calico/issues/2879)

**IP-in-IP** — используется, когда физическая сеть между нодами **не умеет** маршрутизировать IP-адреса подов (например, в облаке AWS/GCP роутеры знают только про IP самих VM, а не про виртуальные IP подов внутри них). Calico берёт оригинальный пакет (`от пода А к поду Б`) и **целиком заворачивает его внутрь другого IP-пакета** — снаружи новый пакет выглядит как "от ноды 1 к ноде 2", а сеть между нодами просто видит обычный трафик между двумя реальными хостами, не подозревая о существовании подов внутри. Именно из-за этого у вас и появился интерфейс `tunl0` — это и есть точка входа/выхода для этой "обёртки". [docs.tigera](https://docs.tigera.io/calico-cloud/networking/configuring/vxlan-ipip)

**VXLAN** — то же самое по смыслу (заворачивание пакета), но использует другой протокол инкапсуляции (UDP+VXLAN вместо чистого IP-in-IP) и **не требует BGP вообще** — маршруты распространяются через саму Kubernetes API, а не через отдельный BGP-протокол между нодами. Из-за этого VXLAN проходит даже там, где сетевые правила блокируют "нестандартные" IP-протоколы (IPIP технически использует IP-протокол номер 4, который иногда фильтруют файрволы облаков и корпоративных сетей — VXLAN использует обычный UDP, который блокируют реже). [besthub](https://www.besthub.dev/articles/deep-dive-into-calico-s-underlying-communication-bgp-ipip-and-vxlan-modes-e32f843b1ea6)

## Что стоит за настройками `Always` / `CrossSubnet` / `Never`

Это не отдельные режимы, а **режим применения** инкапсуляции — вы уже видели их в конфиге вашего Calico:

```
CALICO_IPV4POOL_IPIP: Always
CALICO_IPV4POOL_VXLAN: Never
```

- **`Always`** — заворачивать вообще весь трафик между подами разных нод, даже если они физически в одной L2-сети.
- **`CrossSubnet`** — заворачивать только трафик, который пересекает границу подсети (то есть между нодами в одной подсети пакеты идут "напрямую" без оверхеда, а между разными подсетями — с инкапсуляцией). Это разумный компромисс, который использует BGP для обнаружения топологии сети. [docs.platform9](https://docs.platform9.com/managed-kubernetes/5.7/networking/networking-integration-with-calico)
- **`Never`** — вообще не заворачивать, полагаться только на чистый BGP-роутинг.

## Как это применимо конкретно к вашему кластеру

У вас все три ноды сидят в **одной** L2 host-only подсети (`192.168.56.0/24`) — а это ровно тот случай, когда полный `Always`-IPIP избыточен. Раз все ноды и так физически видят друг друга напрямую без роутеров между собой, инкапсуляция вам не нужна вообще — вы просто теряете немного производительности и MTU (пакеты урезаются до 1480 вместо 1500) без всякой выгоды.

Более правильный для вашего случая выбор — **`Never`** (чистый BGP), потому что:

- вся сеть уже плоская (L2), маршрутизировать напрямую можно без проблем;
- вы получаете нулевой оверхед и полный MTU 1500;
- это заодно хороший повод разобраться, как реально работает BGP-роутинг между Calico-нодами — практическая часть той самой "продвинутой сети", которая у вас в интересах.

## Подготовка: нужен под на другой ноде

Проблема: сейчас **все** ваши прикладные поды (`nginx-test`, `coredns`) сидят на **node3** — они не пересекают границу между нодами вообще, поэтому эффект инкапсуляции не увидеть. Нужно временно посадить тестовый под на node1, чтобы был реальный межнодовый трафик.

**На хосте:**

```bash
kubectl run test-node1 --image=busybox --restart=Never \
  --overrides='{"spec":{"tolerations":[{"key":"node-role.kubernetes.io/control-plane","operator":"Exists","effect":"NoSchedule"}],"nodeSelector":{"kubernetes.io/hostname":"node1"}}}' \
  -- sleep 3600
```

Флаг `tolerations` временно "прощает" тот самый taint control-plane, который мы обсуждали (`NoSchedule`), чтобы busybox можно было насильно посадить на node1.

```bash
kubectl get pods -o wide
```

Убедитесь, что `test-node1` в `Running` на node1, и запомните его IP (будет из диапазона `10.244.x.x`, отличного от `10.244.135.x` — блок node3).

```
NAME         READY   STATUS      IP              NODE
nginx-test   1/1     Running    0.244.135.4      node3
test-node1   1/1     Running    10.244.166.129   node1
```

Ставим `tcpdump` там, где будем смотреть трафик:
**На node1 и на node3:**

## Часть 1. Baseline — текущий режим (IPIP Always)

**На node1** (в отдельном терминале, оставляем работать):

```bash
sudo tcpdump -i enp0s8 -n host 192.168.56.103 -c 10
```

Слушаем трафик к node3 на "физическом" интерфейсе (не на `tunl0`) — если пойдёт IPIP-инкапсуляция, мы увидим её именно здесь, обёрнутую в обычный IP.

**На хосте** (в другом терминале — инициируем трафик):

```bash
kubectl exec test-node1 -- ping -c 5 <IP_пода_nginx-test_на_node3>
```

В выводе `tcpdump` на node1 ищите строку с `IP 192.168.56.101 > 192.168.56.103: IP 10.244.166.x > 10.244.135.x: ICMP echo request` — это и есть IP-in-IP: пакет от 192.168.56.101 к 192.168.56.103 **внутри которого** лежит второй IP-пакет с настоящими адресами подов. Двойной `IP` в строке — это и есть визуальный признак инкапсуляции.

## Что вы должны заметить по итогу

Самое наглядное отличие — **скорость переключения**: у Calico это происходит "на лету", без перезапуска подов и без простоя (в отличие от смены `pod-network-cidr`, которую нельзя поменять без пересоздания кластера). Это потому что режим инкапсуляции — решение конкретно про то, **как** пакет летит по проводу между нодами, а не про то, какие IP выданы подам — сама адресация не меняется ни на секунду.


Ошибка ожидаемая — `ping` внутри контейнера пытается создать "сырой" (raw) ICMP-сокет, а для этого нужна capability `CAP_NET_RAW`, которую CRI-O по умолчанию не даёт обычным подам без явного запроса в манифесте. Именно поэтому в tcpdump вы увидели только служебный трафик кластера (`kube-apiserver` на `6443` между node1 и node3) — ваш `ping` вообще не успел отправить ни одного пакета.

Два варианта решения — попроще (обойти ping) и правильнее (дать capability явно).

## Вариант 1 (быстрее) — использовать HTTP вместо ICMP

У вас уже есть готовая цель — `nginx-test` на node3 слушает порт 80. BusyBox умеет `wget`, задействуем TCP-трафик вместо ICMP — для наблюдения инкапсуляции разницы никакой, пакеты всё равно идут между теми же двумя нодами.

**На хосте**, узнаём IP nginx-test (если забыли):

```bash
kubectl get pod nginx-test -o jsonpath='{.status.podIP}'
```

**На node1**, запускаем tcpdump (как раньше):

```bash
sudo tcpdump -i enp0s8 -n host 192.168.56.103 -c 10
```

**На хосте**, в другом терминале, инициируем трафик:

```bash
kubectl exec test-node1 -- wget -qO- http://<IP_nginx-test>
```

В tcpdump на node1 должны появиться пакеты именно к порту `80` (внутри инкапсуляции, если IPIP включён) — ищите `IP 192.168.56.101 > 192.168.56.103: IP 10.244.166.129.xxxxx > 10.244.135.4.80`.

## Вариант 2 (правильнее) — пересоздать под с нужной capability

Если хочется именно `ping`, пересоздайте тестовый под с явным разрешением на raw-сокеты:

**На хосте:**

```bash
kubectl delete pod test-node1
kubectl run test-node1 --image=busybox --restart=Never \
  --overrides='{"spec":{"tolerations":[{"key":"node-role.kubernetes.io/control-plane","operator":"Exists","effect":"NoSchedule"}],"nodeSelector":{"kubernetes.io/hostname":"node1"},"containers":[{"name":"test-node1","image":"busybox","command":["sleep","3600"],"securityContext":{"capabilities":{"add":["NET_RAW"]}}}]}}' \
  -- sleep 3600
```

Тут я явно прописал весь блок `containers`, потому что `--overrides` заменяет секцию `spec` целиком — нельзя просто добавить `securityContext` отдельно, не переопределив заодно `image`/`command`, иначе Kubernetes не поймёт, что запускать.

Проверка:

```bash
kubectl exec test-node1 -- ping -c 5 10.244.135.4
```

Теперь `ping` должен отработать без ошибки `permission denied`.
